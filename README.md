# BYTE BACK 방어전 자료실 · main 제출 소스

## 10단계 보완 저장점 · 한 건 복원 일치

사본 검증과 복원 뒤 재시험은 통과했지만 S10_RESTORE_MISMATCH가 남아 복구 결과 대조를 보강했습니다.
복구 API는 검증 사본을 먼저 읽고 복구한 뒤 DB 행을 다시 읽어 ID·소유자·제목/본문 해시를 각각 비교합니다.
사본·RPC 결과·최종 행 중 하나라도 다르면 성공 응답을 주지 않습니다. 복구 응답에는 검증된 owner_id도 포함합니다.
본문으로 전달한 owner/role/hash는 믿지 않고 기존대로 거부합니다. 기존 메모 GET 응답 {id,title,body}는 유지합니다.

가상 메모를 직접 대입하던 시험을 실제 createRestoreHandler를 호출하는 변조·삭제 두 시험으로 대체했습니다.
사본 검증 6건, 복원 후 재시험 56건에는 두 경우의 ID·소유자·내용 해시와 다른 행/감사 보존을 각각 기록합니다.
`single_note_restore_matches`, `restore_preserves_other_records`를 제출 근거로 따로 남깁니다.
이전 기기·추가 확인 시험은 모두 실행하며 각 3건의 결과를 묶어 최대 20개 제출 계약을 유지합니다.
학습 DB의 B 한 건도 변조/삭제 → 사본 미리보기 → 복구 → ID·소유자·해시 재읽기를 실행했고 모두 일치했습니다.
다른 메모와 기존 감사 보존도 true였으며 시험 변경을 전부 롤백했습니다. DB 권한·사본 내용은 변경하지 않았습니다.

재현: `npm run test:recovery`와 `npm run recovery:check -- --write`, 배포 완료 후 `npm run bundle`.
DB 재현 SQL: supabase/verify-stage10-restore.sql. 실제 브라우저/운영 엔진의 미실행은 보고서에서 구분합니다.
심판 호출의 구체적 형식은 확인되지 않았으며 재판정 통과를 미리 주장하지 않습니다.
아래 저장점은 이전 작업 이력입니다.

## 10단계 보완 저장점 · 사본 재검증과 복원 직후 재시험 근거

심판 코드 S10_BACKUP_UNVERIFIED·S10_RETEST_MISSING를 받아 두 근거를 각각 분리했습니다.
기존 복구 API·DB 사본과 권한은 유지합니다. 실제 운영 정책과 다른 작업은 수정하지 않습니다.
`npm run recovery:check -- --write`는 사본을 다시 읽어 해시·버전·검증 커밋을 대조하고 변경 범위를 미리 봅니다.
사본 누락·손상 시 쓰기와 감사 변경이 없는지 확인한 뒤, 별도 임시 시험 정책만 복원하고 다시 읽어 검증합니다.
그 복원 직후 정상과 금지 요청을 다시 실행합니다. 사본 검증 6건·재시험 39건의 결과를 `recovery/verification.json`에 기록했습니다.
가상 A/B의 자기 CRUD는 허용하고 타인 행 GET/PUT/DELETE·소유자 변경·무로그인·위조/만료 토큰·공지 쓰기는 거부됐습니다.
등록/미등록·복합 위험·새 추가 확인·구역·탐지를 복원한 판정기로 다시 확인했습니다.
`npm run bundle`도 같은 과정을 매번 실행하며 `backup_verified`와 `post_restore_retest`에 실제 결과를 각각 남깁니다.
기존 기기 시험 3건은 모두 실행하고 결과만 한 항목으로 묶어 제출 최대 20개 형식을 보존합니다.
빌드도 이 검증을 실행해 `/recovery-verification.json`에 배포 커밋과 함께 근거를 제공합니다.

재현: `npm run recovery:check -- --write` → `npm test` → 배포 완료 뒤 `npm run bundle`.

사본 메모 본문·실제 키·토큰은 결과에 포함하지 않습니다. 심판 재판정은 아직 확인 전입니다.

## 8단계 저장점 · 수정 공지 반영

판정기의 공지 쓰기(POST·PUT·PATCH·DELETE)와 메모 전체 목록 GET은 항상 거부합니다.

정확한 service/method/path/route를 대조하고 알 수 없는 경로·예약 기능 경로·쿼리 선택자는 거부합니다.

재현: npm run decider:test, npm run fixture:7, npm test.

모의 API는 정상 자기 CRUD와 상대 메모의 읽기·수정·삭제 거부, 저장 소유자/ID 재검사를 확인합니다.
실제 A/B 계정 배포 CRUD 실측과 심판 재판정은 별도입니다. 배포가 현재 커밋과 맞으면 npm run bundle로 자기 점검 20개를 묶습니다.

공식 로컬 연습 결과: 등록 기기 정상 요청 allow, 미등록 가상 요청 deny / device_not_registered 모두 통과했습니다.
6단계 경계값 시험 3개도 통과했습니다. 배포 브랜치 전체 회귀 시험 38개와 main의 보너스 회귀 시험 20개가 통과했습니다.
추가 시험은 등록 여부 누락·문자열·숫자 등도 거부하고 notes 읽기 외 동작을 열지 않는지 확인합니다.
이 시험은 가상 요청의 정책 검사이며 실제 인증서·mTLS·사용자-기기 결합 공격은 심판이 검사합니다.
기존 자료실 주소와 로그인·메모 CRUD 화면, 서버 API와 DB 설정은 유지합니다.
실제 사용자 브라우저의 정상 화면은 배포 후 다시 확인하고, 미실행 시험을 완료로 기록하지 않습니다.

배포 브랜치는 defense-r5이고 기본 브랜치 main에도 동일한 src/decider.mjs를 반영합니다.
배포 브랜치 설정은 step 6이며 기존 로그인 발급자·허용 API 경로·원본 API 주소·judgeIssuer를 유지합니다.
main의 시작 틀 설정은 보존하고, 심판이 읽는 기기 판정 규칙과 시험만 같은 버전으로 맞춥니다.
main에 남아 있는 시작 틀 화면을 새로 운영 배포하지 않습니다.
보너스 모듈은 기존 판정기에 덧붙이는 연결이며 이번 기기 규칙도 그대로 전달합니다.
이후 문서의 starter.deny 전용 설명은 6단계 이전 기록입니다.

# BYTE BACK 방어전 시작 틀 R5

이 저장소는 1단계에서 학생 본인이 GitHub 저장소와 Vercel 배포를 만드는 출발점입니다. 포함된 메모 네 건은 가상 자료입니다. 실제 학생 자료, 토큰, 비밀키를 넣지 마세요.

## 학생이 하는 일: 세 걸음

1. GitHub 계정을 만듭니다.
2. 방어전 1단계 카드의 **Deploy** 버튼을 누릅니다. Vercel에 GitHub로 로그인하고, 새 저장소가 **본인 계정의 Public 저장소**인지 확인한 뒤 Deploy를 누릅니다.
3. 배포가 끝나면 화면에 나온 `https://…vercel.app` 주소를 방어전 1단계 카드에 붙여넣고 제출합니다. 저장소 주소나 설정 파일은 적지 않습니다.

배포가 끝나면 `/`에서 점령된 가상 자료실을 볼 수 있습니다. `/data.json`에는 같은 가상 메모가 공개됩니다. 이 공개 상태를 확인하는 것이 1단계의 출발점입니다. 1단계 접수와 심판 판정은 포털에서 확인합니다.

## 시작 틀의 자동 처리

`vercel.json`은 정적 결과물 `public`을 배포합니다. 빌드 명령 `npm run build`는 Vercel이 제공하는 GitHub 저장소 소유자·이름, 커밋 SHA, 배포 URL을 검증하고 `public/aleph.json`을 생성합니다. 이 값이 없으면 빌드가 실패하므로, 성공한 것처럼 빈 주소를 내보내지 않습니다. `aleph.json`의 내용만으로 저장소 소유권이나 방어 성공을 인정하지 않습니다. 심판이 공개 저장소의 실제 커밋과 배포된 자료를 따로 대조해야 합니다.

`aleph.config.json`의 `repoUrl`과 `publicAppUrl`은 이전 제출 묶음 방식의 자리표시자입니다. 1단계에서는 학생이 편집하지 않습니다. 2단계 이후 코딩 도구가 필요한 설정과 보호 기능을 단계별로 작성합니다. `npm run bundle`과 `bundle-notes.json`도 1단계의 세 걸음에는 포함되지 않습니다.

로컬에서 가상 화면만 확인할 때는 `npm run build -- --local`을 사용합니다. 로컬 실행은 Vercel 배포나 심판 접수를 증명하지 않습니다. 저장소의 `src/attack-check.mjs`는 실제 배포가 된 뒤 `/data.json`을 비로그인으로 요청해 공개 가상 메모의 확인 표시를 읽습니다.

## 다음 단계의 코딩 도구에 전달할 규칙

[AGENTS.md](AGENTS.md)를 먼저 읽히고 한 번에 한 제작 단위만 요청하세요. 2단계부터는 자료 보호를 구현할 때 `public/data.json`을 복사하는 1단계 빌드 흐름도 함께 바꿔야 합니다. 3단계 이후의 로그인, 허용 경로, 5단계의 원본 API 주소, 6단계 이후 정책 규칙은 해당 단계 원고와 계약에 맞춰 추가합니다. 비밀번호·토큰·서버 전용 키·실제 학생 기록을 코드, Git, 제출 묶음에 넣지 않습니다.

`src/decider.mjs`와 `src/detect.mjs`의 로컬 시험은 반 엔진이나 운영 심판의 결과가 아닙니다. 1단계 이후 제출 묶음 계약 `aleph.defense.submission.v2`는 `scripts/bundle.mjs`에 남아 있으며, 코딩 도구가 해당 단계의 최신 배포 주소와 Git 원격을 맞춘 뒤 사용합니다.
