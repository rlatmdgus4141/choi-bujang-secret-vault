# 보너스 xdr-01: 무차별 로그인 탐지

## 경보와 실행기 출처

공식 저장소 `ChoiTimo/aleph-defense-starter`의 커밋
`2cd777b452525b95e29f12f2c76d9190a594ec23`에서 다음 파일만 원본 그대로 가져왔습니다.

- `xdr/fixtures/brute-force.json` (Git blob `5180c420756dd6e8d8b73ca8ccffe11926e4f754`)
- `scripts/xdr-run.mjs`
- `xdr/README.md` (`defense-r5`; `main`은 기존 시작 틀 안내 보존)

경보는 문서용 주소와 가상 계정을 사용하는 수업용 자료입니다. 실제 Wazuh 로그가 아닙니다.
원본 경보 28건을 수정하거나 새 정답·가짜 경보로 대체하지 않았습니다.
읽기 모듈은 경보 28건에서 5개 필드의 줄 28개를 만들고 비밀값처럼 보이는 값을 가립니다.
원문 로그·비밀번호·키·토큰은 결과 JSON과 알림 로그에 넣지 않습니다.

## 근거와 정책

패턴은 `patterns.json`과 독립 판단 파일 맨 위 상수에 동일하게 둡니다.

| 패턴 | 찾는 신호 | 근거 |
| --- | --- | --- |
| repeated_login_failures | 같은 출발 주소·계정에서 다수 인증 실패가 요약됨 | [MITRE T1110.001](https://attack.mitre.org/techniques/T1110/001/) |
| password_spraying | 같은 주소에서 여러 계정에 같은 비밀번호를 넣었다는 경보 증거 | [MITRE T1110.003](https://attack.mitre.org/techniques/T1110/003/) |
| multi_account_failures | 많은 계정을 바꿔 가며 반복 실패하고 자동화 정황이 있음 | [MITRE T1110](https://attack.mitre.org/techniques/T1110/) |

Wazuh의 횟수·시간 구간·동일 출발 주소·동일 계정 상관 규칙도 참고했습니다.
공식 문서: https://documentation.wazuh.com/current/user-manual/ruleset/ruleset-xml-syntax/rules.html

이 실습의 경보는 이미 상관된 실패 건수를 `data.count` 문자열로 제공합니다.
판단 파일은 개별 경보 하나만 받아 이 요약과 수준·MITRE 표식·설명을 함께 비교합니다.
실패 30건 이상, 동일 비밀번호 대입 계정 5개 이상, 반복적인 다계정 실패 15개 이상을
자동 차단 후보 기준으로 삼습니다. 차단에는 유효한 주소·계정, 수준 10 이상,
T1110 관련 표식과 일치하는 실패 근거가 모두 필요합니다.
명시된 시간 구간이 5분을 넘거나 건수 증거가 서로 다르면 자동 차단하지 않습니다.
경보에 시간 구간이 없을 때는 이미 상관된 높은 수준의 실패 요약만 사용하며,
각각의 단일 실패를 근거 없이 누적하거나 짧은 시간으로 꾸미지 않습니다.

적은 실패나 상관 증거 부족은 알림으로 남깁니다. 성공·로그아웃·세션 유지 등은 기록합니다.
비밀번호 원문을 읽거나 같다고 비교하지 않습니다. 스프레이 판단은 경보의 요약 증거에 의존합니다.
이 횟수·시간·수준은 보수적인 학습용 정책이며 MITRE의 고정 기준이 아닙니다.
확신도 0.85 이상은 block, 0.5 이상은 alert, 나머지는 record입니다.
정상으로 보이는 사건이라도 높은 실패 횟수에 실제 공격 증거가 함께 있으면 별도 검토가 필요합니다.
시험 자료에서 오차가 없었다는 이유로 모든 실제 환경의 오탐이 0이라고 주장하지 않습니다.

## 추가 거부 규칙과 연결

`respond.mjs`가 판단을 다시 계산하고 차단 후보만 새 규칙으로 저장합니다.
5분을 넘긴 경보, 미래 시각 경보, 주소·근거 경보 번호가 없는 경보로 차단 규칙을 만들지 않습니다.
규칙의 유효 시간은 처리 시점부터 15분이며 ID·출발 주소·만료 시각·근거 경보 번호를 포함합니다.
중복 경보는 차단 기간을 연장하지 않으며 만료된 규칙은 조회에 적용하지 않습니다.
파일 기록은 같은 프로세스에서 순서대로 처리하고 임시 파일을 원자적으로 교체합니다.
여러 서버 간 동기화나 영속 저장소 연동이 구현됐다고 주장하지 않습니다.

`createVaultXdrGate`는 기존 `src/decider.mjs` 앞에 덧붙이는 연결 함수입니다.
별도 추가 규칙이 없으면 요청을 수정하지 않고 기존 판정 결과를 그대로 반환합니다.
추가 거부 규칙이 일치하면 호출자가 운영 등록부에 맞게 제공한 거부 응답만 사용합니다.
기존 판정기의 규칙 파일이나 `RULE_IDS`를 수정하거나 허용 규칙으로 대체하지 않습니다.

현행 반 엔진 계약에는 출발 IP가 없으며 기본 판정기는 아직 `starter.deny`입니다.
운영 연결에는 신뢰할 수 있는 서버 출발 주소 제공자와 등록된 거부 응답이 필요합니다.
그 정보가 없는 상태에서 `request.sourceIp`, 사용자 입력 헤더·본문 등을 새 신뢰 값으로 쓰지 않습니다.
정상 요청 통과 검사는 독립된 시험용 기본 정책으로 수행했고 실제 운영 기본 거부 결과도
추가 규칙이 없을 때 그대로 보존되는지 별도로 확인했습니다.
현재 운영 Wazuh 서버, 실제 반 엔진, Vercel 파일 영속 저장 또는 PC 방화벽과 연결한 것은 아닙니다.

## 실행 결과와 다시 확인하기

```sh
npm run xdr:read
npm run xdr:run -- brute-force
npm run xdr:respond -- brute-force
npm run test:xdr
```

공식 실행기의 `result.json`: block 10 · alert 9 · record 9.
가상 시계를 사용한 시험 연결: 차단 후보 10건 거부, 정상 이벤트 9건 중 차단 0건.
알림·기록 이벤트는 추가 규칙 없이 시험용 기본 정책으로 전달됩니다.
현재 실제 ZTNA 기본 규칙은 모든 요청을 거부하므로 시험용 정상 허용과 구분합니다.

검증에는 경보 원본 해시, 읽기 필드·비밀값 가림, 패턴 상수 일치, 입력·순서 독립성,
단일 실패·증거 충돌·느린 시도·정상 성공의 자동 차단 금지, 모듈 한 파일의 격리 실행,
신선도·만료·중복 경보·동시 갱신, 기존 판정 보존과 신뢰 값 선택을 포함합니다.
`decide.mjs`는 import 없이 인터넷·파일·Node 전역이 없는 격리 환경에서 실행됩니다.
판단 파일은 로그나 규칙을 쓰지 않고 `respond.mjs`가 그 작업을 맡습니다.

`xdr/alerts.log`와 `xdr/runtime/`은 로컬 재생 결과이며 Git과 정적 배포에서 제외합니다.
기존 자료실 로그인·메모 CRUD·소유자 검사·DB 권한·5단계 설정은 유지합니다.
제출에는 기존 배포 주소와 공개 GitHub 저장소 주소를 사용합니다.
판정 파일과 결과·근거를 저장소에서 확인할 수 있으며 자기 점검은 심판 점수가 아닙니다.

## 기본 브랜치 제출 위치 보정

보너스 심판이 기본 브랜치 `main`의 옛 커밋을 읽어 판단 파일을 찾지 못했습니다.
`defense-r5`에 있던 보너스 파일을 `main`에도 추가했습니다.
공식 경보·실행기는 두 브랜치에서 동일하며, `main`의 기존 파일과 다른 과제는 보존했습니다.
제출 저장소 루트에서 `xdr/brute-force/decide.mjs`가 보이는지 확인합니다.
자료실 배포는 기존 `defense-r5`를 유지하며 이 보정으로 다시 배포할 필요가 없습니다.
