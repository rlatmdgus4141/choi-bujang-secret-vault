# 8단계 자원 구역과 확인 범위

## 8단계 조회 응답 소유자 검사와 제출 소스 정합성 · 2026-10-13

메모 목록과 한 건 조회는 원본 로그인 도우미가 확인한 사용자 ID로 DB를 조회합니다.
조회 결과의 owner_id를 응답 직전 다시 비교하고 한 건의 id도 요청 경로와 대조합니다.
타인·소유자 누락·다른 자원 행은 본문 없이 거부합니다. 목록에 불일치 행이 하나라도 있으면
전체 응답을 거부합니다. owner_id는 내부 검사에만 쓰며 브라우저 응답은 {id,title,body}입니다.
추가·수정·삭제의 기존 원자적 소유자 조건과 로그인 검증 도우미는 보존합니다.

이번 재현은 DB가 잘못된 소유자의 행을 반환하는 모의 시험입니다. 보완 전에는 200과 본문,
보완 뒤에는 한 건 404 또는 목록 502 JSON 오류이며 정상 자기 조회는 200입니다.
실제 DB는 notes 4건·소유자 2명·소유자 누락 0건, RLS 활성화와 직접 권한 회수를 확인했습니다.
실제 로그인 A/B 토큰으로 배포 API를 호출한 시험은 실행하지 않았습니다.

또한 기본 main 브랜치에 자료 API가 없고 설정은 1단계 자리표시자였던 불일치를 확인했습니다.
현재 자료실의 API·화면·빌드·공개 설정을 main에도 반영하고 기존 XDR와 패키징 작업은 보존합니다.
이 불일치가 심판 실패의 원인이라고 단정하지 않습니다. 기본 decide의 실자원 권한 등록 한계는
아래 기록대로 남아 있으며 API 보완만으로 실제 엔진의 정상 접근까지 검증됐다고 주장하지 않습니다.

검증 결과: 배포 브랜치 npm test 58개, 기본 브랜치 npm test 73개 통과. 기존 XDR 시험도 통과했습니다.
두 브랜치의 로컬 빌드와 현재 정적 파일·최신 소스의 메모 본문/비밀값 검사도 통과했습니다.

다시 확인: npm test, npm run decider:test, npm run build -- --local.
배포 화면에서 자기 메모는 계속 보여야 하며 다른 계정의 메모 ID를 직접 조회하면 404여야 합니다.
현재 커밋이 배포된 뒤 npm run bundle로 제출 묶음을 생성합니다. 심판 재판정은 별도입니다.

## 현재 검증 결론 · 2026-10-13

이전 UUID 형식 검사가 권한 허용을 대신한 결함을 제거했습니다.
판정기에는 서버 소유의 명시적 자원 권한을 초기화하는 createDecider({grants})를 두었습니다.
반·프로젝트·엔진 가명 주체·기기·서비스·HTTP 메서드·정확한 경로·route 8개가 모두 일치해야 허용됩니다.
권한 배열과 각 객체를 복사해 고정하며, 문자열 와일드카드·누락 필드·잘못된 경로는 설정 오류로 거부합니다.
브라우저나 요청의 role/identity/grants/policy는 권한 설정에 쓰지 않습니다.
자원 권한 거부가 재인증보다 먼저입니다. 새 로그인이 권한 없는 자원 접근을 허용하지 않습니다.

기본 decide의 등록 권한은 공식 연습 자원뿐입니다. 실제 엔진의 주체/기기별 등록 목록은 확보되지 않았으므로
미등록 실자원은 deny입니다. 이를 실제 엔진 정상 CRUD 완료나 판정기 단독 DB 소유권 확인으로 기록하지 않습니다.
기존 브라우저는 소유자 검사를 하는 API를 사용하며 이번 변경은 그 API나 DB 권한을 수정하지 않습니다.

- 재현: 이전 decide는 동일 UUID에 서로 다른 두 주체 모두 allow.
- 수정: 등록되지 않은 UUID·목록은 두 주체 모두 deny.
- 가상 권한을 서버에서 등록한 판정기: A/B 자기 자원 GET/PUT/DELETE allow, 상대 자원 deny.
- 명시적 강사 PUT 권한 allow, 학생 role/grants 위조 deny.
- 기기/반/프로젝트/경로 불일치, 권한 객체 사후 변조, fresh login 우회 모두 deny.
- 전체 로컬 시험 55개, 공식 가상 요청 4개 통과. 기존 API의 A/B 소유자 회귀 시험 포함.
- 제출 묶음에는 등록 자기 자원 허용·상대 자원 거부·미등록 UUID/목록 거부의 합동 자기 점검을 기록합니다.
- 실제 심판 통과는 재제출 전 미확인입니다. 아래 이전 기록은 과거 이력입니다.


## 자원과 최종 API

| 자원 ID | 경로 | 허용 조건 |
|---|---|---|
| notes.personal | GET/POST /api/notes, GET/PUT/DELETE /api/notes/:id | 원본 도우미로 로그인 검증; 모든 조회·변경을 확인된 owner_id로 제한 |
| notices.instructor | GET /api/notices, GET /api/notices/:id | 검증된 로그인; 메모 테이블과 분리된 공지만 조회 |
| notices.instructor | POST /api/notices, PUT /api/notices/:id | 검증된 로그인 + Auth Admin 조회의 현재 app_metadata.vault_role이 instructor |

자료 응답은 기존 `{id,title,body}` 형태를 유지하고 응답 헤더 X-Resource-Id로 구역을 구별합니다.
메모 추가는 서버가 owner_id를 정하고, 수정·삭제는 ID와 소유자 조건을 같은 DB 요청에 적용합니다.
타인 메모와 없는 메모는 같은 404 오류입니다. URL의 다른 owner_id/role/action 선택자는 거부합니다.
정확한 경로 외의 중첩 경로·export·인코딩 우회는 거부하고, 선택적 id 쿼리는 경로 ID와 같아야 합니다.
메뉴·본문의 role, user_metadata, 토큰의 임의 강사 주장으로 권한을 부여하지 않습니다.
공지 수정은 매번 서버 Auth Admin에서 현재 권한을 조회하며, 조회 오류·사용자 불일치는 기본 거부합니다.
실제 계정에 강사 권한을 자동 부여하지 않았고 공지 시드도 넣지 않았습니다.
공지를 운영하려면 관리자가 공식 관리 수단에서 대상 사용자의 app_metadata.vault_role을 승인해야 합니다.
일반 사용자가 수정할 수 있는 user_metadata에 역할을 넣으면 안 됩니다.

## 판정기 계약의 한계

공식 docs/DECIDER_REQUEST.md의 18개 필드에는 메모 소유자와 강사 역할이 없습니다.
subjectId는 엔진 가명이며 Supabase 사용자 UUID가 아니므로 임의 비교나 하드코딩을 하지 않습니다.
resource_zones는 검증된 사용자·기기·service·method·path·route가 맞는 경로만 허용하는 1차 검사입니다.
notes와 notices의 서로 다른 서비스/경로 조합, 예약 동작 경로, 불명확한 경로는 기본 거부합니다.
원문 쿼리를 받을 수 없는 판정기는 queryLength가 0인 경로만 허용합니다. API는 같은 ID 선택만 허용합니다.
메모 allow는 소유자 검사 완료를 뜻하지 않으며 최종 API가 반드시 소유자 검사를 수행합니다.
강사 권한 계약이 없는 현재 엔진 경로에서는 공지 변경을 모두 거부합니다.
최종 공지 API의 강사 허용 기능은 구현했지만, 엔진을 거친 실제 강사 수정 실측은 미실행입니다.
기존 device_registered, step_up_required는 유지하고 공지 읽기도 복합 이상 접속 검사를 받습니다.

## DB

supabase/stage8-notices.sql을 적용했습니다. public.notes와 기존 4건은 보존했습니다.
새 public.notices는 0건, RLS 활성화, PUBLIC/anon/authenticated 직접 권한 없음입니다.
service_role은 SELECT/INSERT/UPDATE만 있으며 DELETE·TRUNCATE는 주지 않았습니다.
서버 비밀키는 기존 서버 환경변수에서만 읽습니다. 인증서·CA·개인키는 만들지 않았습니다.

## 두 번째 재현과 보완

UUID 제한 제출(심판 커밋 61f2b768ea92)도 조회 조건에서 실패했습니다.
/notes/demo에 정상 연습 주체와 다른 주체를 넣으면 둘 다 allow인 결함을 직접 재현했습니다.
이 예외를 공식 fixture-7.mjs의 명시적 반·프로젝트·사용자·기기·정확한 읽기 경로에만 묶었습니다.
다른 주체/기기/반/프로젝트는 추가 인증을 마쳤다고 해도 deny입니다.
신뢰하지 않는 identity/role/헤더로 이 결정을 바꿀 수 없습니다. 요청에서 소유자를 학습하거나 캐시하지 않습니다.
source none 실제 접속에는 가상 demo 예외가 적용되지 않습니다. 실제 UUID API는 기존 소유자 검사를 거칩니다.
이 연습 권한 설정은 실계정 소유권 매핑의 대체가 아닙니다. 심판이 사용하는 정확한 입력은 미확인입니다.
